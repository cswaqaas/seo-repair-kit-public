# SEO Repair Kit v2.1.9 Compatibility Audit

Audit date: 2026-07-03  
Baseline: bundled `seo-repair-kit.2.1.8` and Git `HEAD` (`SEO Repair Kit v2.1.8`)  
Candidate: current v2.1.9 working tree with Spam Monitor

## Executive conclusion

The v2.1.9 changes do not broadly overwrite or replace the existing v2.1.8 feature implementations. Most changes in the listed existing files are safe integration changes, release-version updates, future-version label changes, or safer data-retention behavior.

The initial audit identified two issues. Both have now been addressed in the candidate:

1. **Resolved - automatic legacy redirection migration.** The centralized activation/update path now creates the current columns and immediately runs the idempotent in-place row migration.
2. **Resolved - public-request Spam Monitor table checks.** The direct schema check was removed from the general admin-class constructor. Schema creation remains owned by activation and centralized update/repair paths.

No PHP or JavaScript syntax errors were found.

## Verification performed

- Compared all 13 reported modified files against the v2.1.8 Git baseline with whitespace ignored.
- Confirmed the bundled v2.1.8 tree contains the corresponding baseline files.
- PHP lint: **97 files checked, 0 failures** using PHP 8.3.7.
- JavaScript syntax: **43 files checked, 0 failures** using `node --check`.
- Traced plugin bootstrap, admin construction, update/activation paths, database migration calls, deactivation, and uninstall behavior.
- Checked Spam Monitor class loading, AJAX registration, scheduler registration, database creation, menu integration, and page-only asset routing.

This was a source-level and local syntax audit. A real WordPress upgrade/database test was not available in this checkout, so database behavior should still be verified on a disposable copy of a v2.1.8 site before release.

## Resolved findings

### 1. High: legacy redirection rows may stop working after schema upgrade

Files involved:

- `seo-repair-kit.php`
- `includes/class-seo-repair-kit-activator.php`

In v2.1.8, the daily admin table check explicitly called:

```php
SeoRepairKit_Activator::manual_migrate_redirection_table();
```

In v2.1.9 this was replaced with:

```php
SeoRepairKit_Activator::ensure_database_tables();
```

`ensure_database_tables()` calls `run_updates()`. That method calls `srkit_create_log_table()` but does **not** call `migrate_redirection_table()` or `manual_migrate_redirection_table()`.

`dbDelta()` can add `source_url` and `target_url`, but it does not copy values from legacy `old_url` and `new_url`. The migration method contains the required copying logic, but now it is reached only through the manual migration UI/AJAX path.

Impact is limited to sites that still have a legacy-only redirect table, but on such a site existing redirects may appear empty or cease matching after the new columns are added.

Resolution: `run_updates()` now calls `self::migrate_redirection_table()` immediately after `srkit_create_log_table()`. This keeps the safer v2.1.9 in-place approach: existing IDs and old columns are preserved, populated current rows are not overwritten, and no table is dropped.

### 2. Medium: Spam Monitor database checks can affect public request performance

Files involved:

- `includes/class-seo-repair-kit.php`
- `admin/class-seo-repair-kit-admin.php`
- `includes/spam-monitor-backend/class-srk-spam-monitor-db.php`

`Seo_Repair_Kit::define_admin_hooks()` constructs `SeoRepairKit_Admin` without an `is_admin()` guard. The v2.1.9 constructor now immediately calls `SRK_Spam_Monitor_DB::maybe_create_tables()`.

`maybe_create_tables()` checks all four active Spam Monitor tables with `SHOW TABLES LIKE ...`. Consequently, ordinary front-end requests can perform these database checks even though they do not use the Spam Monitor admin UI.

This does not alter existing feature results, but it is an avoidable site-wide performance regression.

Resolution: the constructor-level `SRK_Spam_Monitor_DB::maybe_create_tables()` call was removed. Activation, the centralized version-update path, and the daily admin repair path continue to create or upgrade the tables. Spam Monitor hook registration remains available for admin AJAX and scheduled scans without adding schema-discovery queries to normal public requests.

## Safe compatibility observations

- Existing dashboard, Links Manager, Robots/LLMs, settings, public robots, deactivation, and core public hooks were not removed by the Spam Monitor work.
- Spam Monitor tables use separate `srk_spam_monitor_*` names, avoiding collision with v2.1.8 tables.
- Deactivation preserves feature data and removes only Spam Monitor scheduled hooks and locks.
- Uninstall now defaults to preserving all customer data, which is safer for accidental deletion/reinstallation.
- The revised redirection migration updates legacy rows in place and preserves record IDs; that implementation is safer than dropping and rebuilding the table once it is restored to the automatic upgrade path.
- Spam Monitor page assets are scoped by the page slug. There is some duplicate registration/enqueueing of the main Spam Monitor style in the admin coordinator and Spam Monitor class, but WordPress handle de-duplication prevents duplicate output; consolidating ownership would still improve maintainability.

## Release recommendation

Status: **code-level issues resolved; runtime upgrade smoke test still required**.

Before releasing v2.1.9:

1. Run a disposable WordPress upgrade with a legacy-only redirection table and confirm IDs, source URLs, target URLs, and redirect behavior remain intact.
2. Profile a normal public request and confirm no Spam Monitor `SHOW TABLES` queries originate from the admin constructor.
3. Run an upgrade smoke test covering Dashboard, Links Manager, Redirects, 404 Monitor, Schema, Meta Manager, KeyTrack, Robots/LLMs, settings save, cron, admin AJAX, and the public front end.
4. Confirm the new activation-email `Reply-To` address and update README release metadata.

After a successful database upgrade and functional smoke test, the existing-file changes are reasonable for v2.1.9 and the Spam Monitor integration can be considered behavior-preserving for the v2.1.8 feature set.
